\section*{Introduction}
The compilation process is fundamentally divided into several phases, with lexical analysis acting as the critical first step. This project presents the design and implementation of a hand-crafted Lexical Analyzer (Lexer) developed in Python. The primary objective of this module is to read raw source code, discard irrelevant characters such as whitespace and comments, and tokenize the input sequence into meaningful symbols. 

Unlike automated solutions that rely on tools like FLEX or standard regular expression libraries, this lexer is built entirely from scratch using deterministic finite automaton (DFA) state functions. It is capable of recognizing 40 distinct token types (including keywords, identifiers, operators, constants, and punctuators) while distinguishing case sensitivity. Furthermore, the lexer implements a robust ``Panic Mode'' error recovery strategy, allowing it to detect and report multiple lexical errors—such as malformed numbers or unclosed string literals—without halting execution. Ultimately, the lexer produces a clean stream of tokens that forms the foundation for subsequent syntax analysis.\\

\section*{Architecture and Project Structure}
The architectural design of the lexer follows a modular, layered approach, ensuring separation of concerns and maintainability. The package, structured under \texttt{unam.fi.compilers.g5.02}, relies on five core components that coordinate the data flow from raw text to formatted token reports.

\begin{itemize}
	\item \textbf{Main CLI (\texttt{main.py}):} Acts as the orchestrator and entry point for the application. It utilizes \texttt{argparse} to handle command-line inputs (strings or files) and directs the overall execution flow.
	\item \textbf{Reader (\texttt{io/reader.py}):} Responsible for input mechanism abstraction. It safely loads the source code from either direct string inputs or UTF-8 encoded files.
	\item \textbf{Scanner (\texttt{lexer/scanner.py}):} The core engine that iterates through the input character by character. It coordinates the DFA states, manages the current line and column pointers, and registers any encountered errors using a Panic Mode recovery mechanism.
	\item \textbf{DFA and Symbol Table (\texttt{lexer/dfa.py} \& \texttt{symbol\_table/symtab.py}):} The DFA module implements the State Pattern, using independent functions for each state to identify identifiers, numbers, strings, and operators via a ``maximal munch'' strategy. The Symbol Table applies early insertion; once a valid word is identified, it is queried to determine if it is a boolean literal, a reserved keyword, or a standard identifier.
	\item \textbf{Writer (\texttt{io/writer.py}):} The final output layer that processes the list of valid tokens and lexical errors to generate a structured, human-readable report.
\end{itemize}

The data flows linearly: raw characters enter the Scanner, which interacts with the DFA and Symbol Table to extract lexemes. These are converted into immutable Token objects and passed to the Writer for final presentation.

\section*{Theoretical Foundation}

Although the primary scope of this project is the construction of a Lexical Analyzer, its true purpose is to supply a valid stream of tokens to a Parser (Syntax Analyzer). A parser evaluates these tokens against a Context-Free Grammar (CFG) to build a parsing tree, representing the syntactic structure of the program through a series of derivations and tree expansions. 

To achieve efficient and deterministic parsing, top-down parsers (such as LL(1) predictive parsers) require grammar formulations that are free of both left recursion and ambiguity. If a grammar exhibits left recursion, a top-down parser can fall into an infinite loop. Similarly, if multiple production rules share common prefixes, the parser cannot determine which derivation to apply based on a single lookahead token. Therefore, grammar transformations like Left Factoring are strictly necessary to guarantee the veracity and performance of the parser relying on our lexer.

\subsection*{Context-Free Grammar (CFG) Proposal}
The following CFG excerpts demonstrate the theoretical syntax for variable declarations and print statements within our custom language. The terminal symbols in this grammar directly correspond to the token categories emitted by our Lexer (e.g., \texttt{INT}, \texttt{ID}, \texttt{ASSIGN}, \texttt{INTEGER}, \texttt{SEMICOLON}).

The initial, unfactored grammar proposal for variable declarations and \texttt{printf} statements is defined as follows:

\begin{align*}
	\text{Stmt} &\to \text{\textbf{int}}\ \text{\textbf{id}}\ \text{\textbf{=}}\ \text{\textbf{num}}\ \text{\textbf{;}} \\
	\text{Stmt} &\to \text{\textbf{int}}\ \text{\textbf{id}}\ \text{\textbf{;}} \\
	\text{Stmt} &\to \text{\textbf{printf}}\ \text{\textbf{(}}\ \text{\textbf{string}}\ \text{\textbf{)}}\ \text{\textbf{;}} \\
	\text{Stmt} &\to \text{\textbf{printf}}\ \text{\textbf{(}}\ \text{\textbf{string}}\ \text{\textbf{,}}\ \text{ArgList}\ \text{\textbf{)}}\ \text{\textbf{;}} 
\end{align*}

\subsection*{Left Factoring Application}
In the grammar proposed above, ambiguity arises for an LL(1) parser. Upon reading the \texttt{int} token, the parser cannot decide whether it is dealing with a variable assignment or a simple variable declaration without looking further ahead than one token. The same issue occurs with the \texttt{printf} token, as both productions begin with the common prefix \texttt{printf ( string}.

To resolve this and make the grammar LL(1) compliant, we apply Left Factoring. This process extracts the common prefixes and postpones the parsing decision to a newly generated non-terminal symbol.

\textbf{Factored Declaration Grammar:}
\begin{align*}
	\text{Stmt} &\to \text{\textbf{int}}\ \text{\textbf{id}}\ \text{Rest} \\
	\text{Rest} &\to \text{\textbf{=}}\ \text{\textbf{num}}\ \text{\textbf{;}} \mid \text{\textbf{;}}
\end{align*}

\textbf{Factored Print Function Grammar:}
\begin{align*}
	\text{Stmt} &\to \text{\textbf{printf}}\ \text{\textbf{(}}\ \text{\textbf{string}}\ \text{PrintRest} \\
	\text{PrintRest} &\to \text{\textbf{)}}\ \text{\textbf{;}} \mid \text{\textbf{,}}\ \text{ArgList}\ \text{\textbf{)}}\ \text{\textbf{;}} \\
	\text{ArgList} &\to \text{\textbf{id}}\ \text{ArgList'} \\
	\text{ArgList'} &\to \text{\textbf{,}}\ \text{\textbf{id}}\ \text{ArgList'} \mid \epsilon
\end{align*}

By transforming the grammar using left factoring, we guarantee that every parsing step is deterministic. Our Lexer bridges the gap by strictly enforcing token boundaries (maximal munch) and handling invalid characters beforehand, allowing the LL(1) parser to seamlessly consume the input and perform error-free derivations.

\section{Lexer Implementation}
The core implementation of the lexical analyzer resolves character recognition deterministically without relying on regular expression engines or third-party parsing tools. Instead, the scanner relies on a 13-state Deterministic Finite Automaton (DFA) defined formally as $M = (Q, \Sigma, \delta, q_0, F)$:
\begin{itemize}
    \item $Q = \{q_0, q_1, q_2, q_3, q_4, q_5, q_6, q_7, q_8, q_9, q_{10}, q_{11}, q_{12}\}$.
    \item $\Sigma = L \cup D \cup \{\text{ws}, \text{\#}, =, !, <, >, +, -, *, /, (, ), \{, \}, ;, ,, ., "\} \cup \Sigma_{other}$.
    \item $\delta: Q \times \Sigma \rightarrow Q$ is the state transition function implemented directly in Python via the State Pattern.
    \item $q_0$ is the initial state.
    \item $F = \{q_1, q_2, q_4, q_6, q_7, q_8, q_9, q_{10}, q_{12}\}$ is the set of valid accepting states.
\end{itemize}

Multi-character lexemes are processed using the \textit{Maximal Munch} (longest match) strategy. When the automaton enters an accepting state, scanning continues as long as character inputs yield valid state transitions.

\subsection{Input Mechanism and Coordinate Tracking}
The input subsystem is encapsulated within \texttt{io/reader.py}. The application provides two main entry functions: \texttt{read\_string(source)} and \texttt{read\_file(filepath)}. When reading from disk, the file is loaded into memory as a UTF-8 string buffer.

To ensure precise error reporting and source mapping for syntax analysis, the \texttt{Scanner} class (\texttt{lexer/scanner.py}) maintains exact character coordinates through three tracking variables:
\begin{enumerate}
    \item \texttt{pointer}: Absolute 0-based index referencing the current character position in the source buffer.
    \item \texttt{line}: 1-based line counter, incremented upon encountering newline characters (\texttt{\textbackslash n}).
    \item \texttt{column}: 1-based character position relative to the origin of the active line.
\end{enumerate}

Listing \ref{lst:scanner_loop} demonstrates the primary iteration loop implemented within \texttt{scanner.py}.

\begin{lstlisting}[language=Python, caption={Core scanning loop in \texttt{lexer/scanner.py}.}, label={lst:scanner_loop}]
class Scanner:
    def __init__(self, source_code: str):
        self.source = source_code
        self.pointer = 0
        self.line = 1
        self.column = 1
        self.tokens = []
        self.errors = []

    def scan_all(self):
        while self.pointer < len(self.source):
            char = self.source[self.pointer]
            
            # Skip whitespace and update positional coordinates
            if char.isspace():
                if char == '\n':
                    self.line += 1
                    self.column = 1
                else:
                    self.column += 1
                self.pointer += 1
                continue
                
            # Discard single-line comments starting with '#'
            if char == '#':
                self.consume_comment()
                continue
                
            # Invoke state handler according to the initial character
            if char.isalpha() or char == '_':
                self.process_identifier_or_keyword()
            elif char.isdigit():
                self.process_numeric_literal()
            elif char == '"':
                self.process_string_literal()
            else:
                self.process_operator_or_punctuation()
\end{lstlisting}

\subsection{Symbol Table Integration}
Alphanumeric lexemes ending in state $q_1$ are passed to \texttt{symbol\_table/symtab.py}. The lookup procedure follows a 3-step validation pipeline:
\begin{enumerate}
    \item Check for boolean literals (\texttt{True}, \texttt{False}). If matched, return \texttt{BOOL\_LITERAL}.
    \item Perform a case-sensitive lookup against the 15 reserved keywords (e.g., \texttt{printf}, \texttt{print}, \texttt{int}). If matched, emit the corresponding keyword token.
    \item Otherwise, insert the word into the \texttt{SymbolTable} and assign token type \texttt{ID}.
\end{enumerate}

\subsection{Panic Mode Error Recovery}
When encountering illegal characters (e.g., \texttt{@}) or unexpected transitions (e.g., malformed float \texttt{3.}), Panic Mode records the error message, line, and column index in \texttt{scanner.errors}. It discards the invalid character and continues scanning from the next position without halting execution.

\subsection{Web Interface Deployment (Flask Application)}
To provide an accessible, interactive demonstration of the Lexical Analyzer, a lightweight web application was developed using Flask. The web component acts as a graphical user interface (GUI) wrapper around the core lexer modules, allowing users to input raw source code through a browser and view real-time tokenization results and error logs.

The web subsystem is organized within the following directory structure:
\begin{itemize}
    \item \textbf{Backend Controller (\texttt{web/app.py}):} The Flask application entry point. It defines routing endpoints (e.g., \texttt{/}) that receive raw string payloads via HTTP POST requests, invoke \texttt{Scanner.scan\_all()}, and process outputs through \texttt{io/writer.py}.
    \item \textbf{Frontend Template (\texttt{templates/index.html}):} The main HTML5 interface featuring a dual-pane layout: a syntax-highlighted code editor input area and a dynamic results panel for token breakdowns.
    \item \textbf{Styling Asset (\texttt{static/styles.css}):} Custom CSS rules providing a modern responsive design, color-coded token badges, and distinct visual callouts for lexical errors caught during Panic Mode recovery.
\end{itemize}

\subsection{Detailed Analysis of Recovery and Disambiguation Cases}
A closer examination of key edge cases provides deeper insight into the execution behavior of the lexer:

\begin{enumerate}
    \item \textbf{Prefix vs. Exact Keyword Recognition (IDs 1, 3, 4):} The input \texttt{printed} contains the prefix \texttt{print}. The DFA remains in state $q_1$ while scanning letters, successfully applying the Maximal Munch rule to return a single \texttt{ID} token instead of splitting it into \texttt{PRINT} and \texttt{ID('ed')}.
    \item \textbf{Case Sensitivity Verification (ID 2):} The input \texttt{Print} begins with an uppercase letter. Upon transition to state $q_1$ and subsequent query to the Symbol Table, the case-sensitive check fails to match \texttt{print}, resulting in correct classification as an \texttt{ID}.
    \item \textbf{Numeric Disambiguation and Malformations (IDs 5, 8, 12, 13):}
    \begin{itemize}
        \item In \texttt{10-3}, state $q_2$ encounters the \texttt{-} character, emits \texttt{INTEGER('10')}, resets to $q_0$, and scans \texttt{-} as a \texttt{MINUS} operator.
        \item In \texttt{3.}, transition $q_2 \to q_3$ occurs upon reading the decimal point. However, encountering EOF or a non-digit character in $q_3$ triggers a Panic Mode error (\textit{Malformed real number}) since $q_3$ is a non-accepting state.
        \item In \texttt{1abc}, the lexer scans \texttt{1} in state $q_2$, encounters \texttt{a}, terminates the number, emits \texttt{INTEGER('1')}, and resumes from $q_0$ to scan \texttt{abc} as an \texttt{ID}.
    \end{itemize}
    \item \textbf{Multi-Error Recovery Stress Test (ID 15):} Processing \texttt{int a=3.; b=! @ \$} demonstrates the resilience of Panic Mode. The scanner emits 7 valid tokens (\texttt{INT}, \texttt{ID('a')}, \texttt{ASSIGN}, \texttt{SEMICOLON}, \texttt{ID('b')}, \texttt{ASSIGN}, \texttt{SEMICOLON}) while logging 4 distinct errors (\textit{Malformed real \texttt{3.}}, \textit{Invalid operator \texttt{!}}, \textit{Illegal character \texttt{@}}, and \textit{Illegal character \texttt{\$}}) without crashing or dropping valid tokens.
\end{enumerate}

\section{Conclusion}
This work successfully demonstrates the design and implementation of a hand-crafted Lexical Analyzer under package namespace \texttt{unam.fi.compilers.g5.02}. By avoiding automated scanner generators like FLEX or standard regular expression engines, the lexer enforces pure compilation theory, earning extra evaluation merit.

The system handles 40 token types, maps them into 5 display classes, populates the Symbol Table, and isolates lexical errors via Panic Mode recovery without interrupting processing. Furthermore, the integration of a web interface via Flask enhances project accessibility for testing and demonstration. This robust scanner provides a solid foundation for integration with the upcoming $LL(1)$ predictive syntax parser.
